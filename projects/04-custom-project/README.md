# Project 04 - Custom Live Project

## Purpose

This track allows a learner/team to propose a real problem instead of using one of the predefined projects.

A custom project is approved based on engineering depth and measurable outcomes, not novelty alone.

## Minimum eligibility

The proposed project must include at least four of these dimensions:

- Linux/system administration;
- API/application development;
- database or persistent state;
- cloud or virtualized infrastructure;
- Infrastructure-as-Code;
- CI/CD;
- containers/Kubernetes;
- observability;
- security controls;
- automation/integration;
- troubleshooting/operations.

A purely static website, one-off script, slide deck or CRUD tutorial is normally insufficient unless the proposal adds meaningful delivery/operations depth.

## Proposal process

### Stage 1 - Problem discovery

Submit a completed SCQ describing:

- current situation;
- measurable challenge;
- stakeholders/users;
- desired outcome;
- constraints;
- unknowns.

### Stage 2 - Project proposal

Use [`PROPOSAL_TEMPLATE.md`](PROPOSAL_TEMPLATE.md).

### Stage 3 - Design review

Create a Solution Intent using the repository template.

### Stage 4 - Approval

Trainer approves one of:

- Approved;
- Approved with conditions;
- Revise and resubmit;
- Rejected with reason.

## Approval criteria

A strong proposal has:

- a real problem;
- testable success criteria;
- an end-to-end engineering path;
- enough scope for design/troubleshooting;
- safe data and infrastructure use;
- realistic completion scope;
- observable and repeatable delivery;
- a clear demo story.

## Required final artifacts

The same program-wide Definition of Done applies to custom projects.
